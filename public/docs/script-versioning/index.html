Версионирование скриптов синка

При изменении алгоритма синка, сборки матрицы или фоновой задачи нужно поднимать версию в том же PR / той же сессии, что и правка кода. Иначе нельзя отличить снапшот, собранный старым скриптом, от нового.

Зачем​

  • в БД лежит latest-снапшот без привязки к git-коммиту;
  • поддержка и интеграторы (Huckster и др.) спрашивают «какой скрипт отдал эти строки»;
  • багфиксы пагинации/фильтров меняют состав данных — это должно быть видно в UI и API.

Эталон: Huckster​

СлойФайл / место
Реестр ревизийlib/hucksterSyncRevision.js
Алгоритмroutes/exportsHuckster.js, lib/hucksterMsBridgeMatrix.js, lib/hucksterSnapshotStore.js
APIполе sync_script в GET /api/exports/huckster/config, GET …/sync-status, GET …/snapshot, в result после sync
UIбейдж v1.0.4 · rev.5 (текущий) на /exports-huckster.html
Справка APIраздел Exports / Huckster

Пример записи ревизии:

{
  revision: 2,
  version: '1.0.1',
  date: '2026-05-26',
  matrix_kind: 'ms_bridge_v1',
  notes: 'Unit/repricer: offset += длина страницы; …',
}

Когда поднимать версию​

Обязательно:

  • логика пагинации, фильтров, маппинга полей;
  • состав или смысл колонок матрицы;
  • порядок фаз синка (repricer → unit → мост МС и т.д.);
  • багфикс, из‑за которого в выборку попадают/пропадают строки.

Не обязательно:

  • рефакторинг без изменения результата;
  • правки стилей/текстов UI без смены алгоритма;
  • только документация.

Semver (практика)​

Изменениеversionmatrix_kind
Багфикс, тот же формат матрицыpatch (1.0.0 → 1.0.1)без смены
Новое поведение, старые снапшоты читаютсяminor (1.0.1 → 1.1.0)без смены или новый kind с back-compat в UI
Другая схема JSON / колонокmajor или новый kindновое значение, новая ревизия

revision — монотонный счётчик строк в реестре (1, 2, 3…).

Контракт для нового модуля синка​

  1. Создать lib/<name>SyncRevision.js по образцу Huckster.
  2. Экспортировать get<Name>SyncMeta() и использовать только его для версии в рантайме.
  3. Добавить поле метаданных в API статуса/конфига/снапшота.
  4. Писать мету в payload при сохранении в БД.
  5. Показать версию на экране панели (бейдж из API).
  6. Описать поле в api.md и дописать строку в историю на этой странице.
