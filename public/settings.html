Формула продаж / закупки

Параметры для блока «Формула продаж» на карточке товара (предлагаемый неснижаемый). Средний спрос и сумма за период Продажи за период, дней (ключ sales_formula_sales_window_days); дни без остатка — за период Анализ отсутствий, дней (sales_formula_absence_analysis_days), умножаются на тот же средний спрос; затем сумма с учётом отсутствий × Коэффициент пополнения (sales_formula_replenishment_coef) — без прибавки полей «Базовый запас» и «Базовый запас для дорогих…» (они остаются в форме для учёта и возможных доработок). Редкий товар: не дорогой по цене «маркет» и сумма продаж за период «Продажи за период» ≤ 1 шт → сразу Базовый запас для товаров с редкими продажами (sales_formula_rare_base_qty). Далее кратность и Процент от упаковки (если после округления вниз получилось бы меньше 1 шт при положительном черновике — подставляется тот же базовый запас для редких или для дорогих с редкими продажами), затем Макс. изменение только на повышение.

Подсказка по полям и расчёту (как на карточке «Формула этапами»)
  • В шаге «редкий товар» сравнивается только фактическая сумма продаж за окно «Продажи за период, дней», без сложения с «упущенными». Условие: сумма ≤ 1 шт и товар не дорогой (цена с «маркет» в названии ≤ «Порог дорогой товар»).
  • В шаге умножения на коэффициент участвует только (сумма с учётом отсутствий) × Коэффициент пополнения. Поля «Базовый запас» (sales_formula_base_qty) и «Базовый запас для дорогих товаров с редкими продажами» (sales_formula_expensive_rare_min_qty) к этому произведению не добавляются — так зафиксировано в эталонном примере расчёта.
  • «Порог „редкого“, шт/день (legacy)» (sales_formula_rare_avg_max) в формуле не используется.
  • После шага кратности и «Процента от упаковки»: если округление вниз дало бы меньше 1 шт при положительном черновике до шага, подставляется минимум — для не дорогого товара «Базовый запас для товаров с редкими продажами», для дорогого — «Базовый запас для дорогих товаров с редкими продажами» (по проверке дорогости на карточке).

Маркетплейсы: ключи и лимиты API

Единые настройки Ozon, Wildberries и Яндекс Маркета. Принудительное обновление запускается ниже отдельной кнопкой.

Для справки; лимиты WB разные у категорий API (цены ≠ маркетплейс/остатки).

Автосинхронизация по расписанию

Кнопки «Запустить сейчас» отправляют задачу на сервер (очередь + один воркер). Результат последнего нажатия — в плашке ниже; ход выполнения — на странице «Логи фоновых процессов».

Включить

Ежедневный импорт каталога ваших магазинов (Bitrix / Webasyst) в локальную таблицу my_products (страница «Мои товары»): обходит все источники из «Мои сайты», обновляет SKU, цену и остаток, помечает отсутствующие в источнике как is_active=0. Прогресс и статус — на «Логи фоновых процессов» (раздел «Мои товары»).

Включить

Полная выгрузка из API МС в таблицу ms_export для «МойСклад» (номенклатура, остатки, неснижаемый остаток из карточки МС, атрибуты для карточек в БД). Это не импорт отгрузок — отгрузки делают «Продажи МС» (mssales). После успешного сохранения ms_export одним запросом обновляется dg_product_zero_stock_log за сегодня: складская позиция «Да», не архив, остаток ≤ 0 или для кода без «-» остаток < минимального числового суффикса среди номенклатур «тот же код-число» в ms_export (ручная фиксация за тот же день не перезаписывается). «Лимит страницы» и «Задержка» ниже в настройках МС. Прогресс и статус — на «Логи фоновых процессов» (секция «МойСклад: ms_export (МСК)»).

Включить

После успешного ночного (или ручного) обновления маркетплейсов автоматически пишется снимок для страницы «Проблемы с товарами» (фильтр «есть проблемы», исключить комплекты): дата, слот HH:mm из этого поля, число строк и разбивка по менеджерам / контент-менеджерам.

Включить

Ежедневная авторизация в e-teleport (Huckster) под учёткой из настроек ниже (email / password) и обход магазинов из «Набор магазинов 1» / «Набор 2». Сервис строит матрицы рекомендованных цен (Витрина и РРЦ) для страницы «Huckster (РРЦ калькулятор)»: скачивает товары, считает по правилам и сохраняет снапшот в БД (журнал — logs/huckster-sync.log). Прогресс и статус — на «Логи фоновых процессов» (раздел «Калькуляция Huckster»).

Включить

Ежедневный пересчёт двух метрик дашборда одной задачей:
1) Размер БД по information_schema.TABLES (суммарный объём, данные, индексы, число таблиц рабочей БД p_datagon_ru) — эндпоинт GET /api/processes/db-size, виджет «Размер базы данных».
2) Дисковое пространство: рекурсивный обход корня проекта (`node_modules`, `vendor`, `.git`, `docs-docusaurus` и т.д.) с разбивкой по папкам и объёмом ФС через fs.statfs — эндпоинт GET /api/processes/disk-usage, карточка «Дисковое пространство».
Оба результата кэшируются на сервере (TTL ~5 мин); галка управляет их единым ежедневным пересчётом. Прогресс и статус — на «Логи фоновых процессов» (раздел «Размер БД и диска»).

Включить

Аналог кнопки «↗ В МС: все правки» на странице «Габариты»: для всех позиций с пользовательским замером и заполненным uuid в ms_export отправляет PUT в /entity/{product|bundle}/{uuid}. Журнал изменений габаритов хранится в таблице ms_dimensions_log (при успешной выгрузке — action=sync_ms); прогресс и статус — на «Логи фоновых процессов» (раздел «Габариты МС»).

Включить
Дни недели (МСК)
Пусто в БД или все семь галочек — каждый день. Явное «1…7» в БД тоже означает каждый день (чтобы снятие одного дня не схлопывалось обратно в «все»).

Тянет отгрузки entity/demand из МойСклад API за выбранное окно (по умолчанию 90 дней). UPSERT в ms_demand, позиции — в ms_demand_position, резолв до товаров ms_export. Soft-delete для отгрузок, удалённых в МС за тот же период (см. «Продажи МС», фильтр «Удалённые в МС»). Длительность зависит от объёма: на тестовых данных ~8 минут на ~1300 отгрузок за 7 дней; для 90 дней оценочно 1.5–2 часа. Прогресс и финальный статус — на «Логи фоновых процессов» (раздел «Продажи МС»). Можно остановить кнопкой «Остановить» прямо в карточке «Продажи МС». По расписанию — обычный инкрементальный режим (без fresh), отдельно см. «полный синк» справа.

Включить
Дни недели (МСК)
Тот же job, что «Полный синк с нуля» на странице продаж МС: полное окно, без resume, с полной сверкой soft-delete. По умолчанию только вс — удобно раз в неделю на длинном окне.

Не включайте на то же время, что и обычный импорт слева: один процесс ms-sales в памяти — второй старт получит already_running. Задача в очереди автосинка — mssales_full (журнал на processes).

Закупки: кэш формулы и окон (МСК)
Заполняет dg_formula_proposed_cache для дефолтной выборки закупок (без RAM-снимка). Ускоряет сортировку по «Предлагаемый нес.ост.» и колонкам d_*; журнал — purchase_formula_cache на processes.

Журнал запусков автосинхронизации

Таблица auto_sync_runs: каждый запуск задач из расписания или кнопки «Запустить сейчас» (Мои товары, МойСклад, маркетплейсы, Huckster, размер БД, габариты МС, продажи МС и т.д.). На странице Процессы это строки с кнопкой «Лог» (полный текст в поле message). Это не журнал габаритов ms_dimensions_log — у габаритов отдельная карточка ниже. Автоочистка удаляет только завершённые записи (finished_at не пустой) старше указанного числа дней — раз в 12 часов и при старте сервера. Активный running без финиша не удаляется. По умолчанию 180 дней.
