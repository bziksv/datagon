Шаг 1 · Auth / сессии / cookies / login готово

Дата: 2026-10-25 · Код: routes/auth.js, server.js (gate /api), public/login.html, lib/datagonPageRegistry.js#resolveRedirectAfterLogin.

Модель

  • Токен: randomBytes(32) → в БД только SHA-256 hash. Cookie dg_session httpOnly + SameSite=Lax и дубль в localStorage + x-auth-token.
  • Gate: почти весь /api/* требует актёра (исключения: login/logout, CRM clock sync).
  • Пароли: bcrypt cost 10, мин. 15 символов. Лимит сессий (дефолт 1), admin без лимита. TTL 14 дней.
  • Redirect then: только внутренние *.html без .. + проверка матрицы.

Сильные стороны

  • Hash токена в БД; httpOnly cookie; единый текст ошибки логина; revoke сессий при смене пароля / архиве; санитизация redirect.

Findings

high F-AUTH-01 · Session token в localStorage + login JSON
Login отдаёт auth_token; клиент кладёт в localStorage и шлёт x-auth-token. XSS = кража сессии до 14 дней, минуя httpOnly. Fix: cookie-only, убрать token из JSON/localStorage.
high исправлено F-AUTH-02 · Нет rate-limit / lockout на login
Публичный POST /api/auth/login без throttle/CAPTCHA (rateLimit/helmet отсутствуют). Fix: limit_req / 5 попыток на IP+user / backoff + алерт в activity.
2026-10-27 (прод c60e06a): in-memory 5 fails / 15 мин на IP+username → 429 LOGIN_RATE_LIMIT (routes/auth.js). Nginx limit_req / CAPTCHA — отдельно (F-DEP).
high исправлено F-AUTH-03 · Cookie без флага Secure
attachSessionCookie: httpOnly + SameSite=Lax, secure не задан. Fix: secure: true за TLS; те же атрибуты в clearCookie.
2026-10-27 (прод c60e06a): shouldSecureCookie — TLS via X-Forwarded-Proto/req.secure или DATAGON_COOKIE_SECURE; apply + clear.
medium F-AUTH-04 · Смена пароля без текущего (self)
POST /change-password для своего аккаунта не требует old password → украденная сессия = полный захват. Fix: требовать currentPassword для non-admin.
medium F-AUTH-05 · Timing user-enumeration
Нет пользователя → быстрый 401; есть → bcrypt.compare. Fix: dummy bcrypt на miss.
medium F-AUTH-06 · Нет CSRF-токена
Cookie-auth без CSRF token; SameSite=Lax частично закрывает classic CSRF. Fix: double-submit / Strict + отказ от localStorage token (связка с F-AUTH-01).
low F-AUTH-07 · Admin без лимита сессий
Украденные admin-токены живут параллельно. Fix: лимит + UI revoke/list сессий.
low F-AUTH-08 · bcrypt 10; DELETE user без revoke sessions
Поднятие rounds до 12; перед delete — revoke sessions.
info F-AUTH-09 · x-auth-username не используется сервером
Auth только по token. Убрать header с клиента или задокументировать как display-only.

Приоритет фиксов (шаг 1)

  1. P0: Secure cookie + rate-limit login
  2. P0/P1: cookie-only (без localStorage token)
  3. P1: currentPassword; dummy bcrypt
  4. P2: CSRF/Strict; лимит admin; bcrypt 12

Шаг 2 · Матрица доступа + API_PREFIX_RULES готово

Дата: 2026-10-25 · Код: lib/datagonPageRegistry.js, lib/datagonSpecialties.js, middleware в server.js (~3674), HTML gate (~4251), routes/specialties.js.

Модель

  • Специальность → specialty_page_modes (hidden / view / full) на каждый PAGE_DEFS.key.
  • Новые страницы для не-default специальностей дозаливаются как hidden; «Полный доступ» — full.
  • API: API_PREFIX_RULES → pageKey; middleware: hidden→403, view→только GET/HEAD/OPTIONS; admin обходит всё.
  • pageKey == null → ACL не применяется (достаточно сессии).
  • HTML: любой *.html (кроме login/legal/docs/architectui) требует сессию; матрица — только если leaf есть в HTML_FILE_TO_KEY.
  • МП-дочерние: parent exports-marketplaces=hidden, но child view|full открывает HTML; API shop в основном на parent key.
  • can_manage_users: открывает settings HTML + /auth/users* + GET specialties (запись specialties — только admin).

Сильные стороны

  • Единый реестр страниц + режимы; view/full на уровне HTTP-метода; длинные API-префиксы раньше коротких.
  • crm-task-links / product-updates делают доп. assertActorPageAccess внутри роутера (не только prefix).
  • Дочерние МП можно выдать без всего блока parent (HTML) — осознанный UX.
  • Менеджер пользователей не может писать матрицу specialties (только admin).

Findings

high исправлено F-ACL-01 · Fail-open: неизвестный API path = любой авторизованный
if (pageKey == null) return next() в server.js. Любой новый/забытый /api/… без записи в API_PREFIX_RULES доступен всем с сессией. Пример: /something-unknown → NULL. Fix: fail-closed (403 если не matched), whitelist null только для явного списка (/auth/me, track, …).
2026-10-27 (прод c60e06a): resolveApiPathAccess → unmatched 403 API_UNMATCHED; явный pageKey: null только для whitelist-префиксов в API_PREFIX_RULES.
high исправлено F-ACL-02 · Fail-open mode: нет ключа в page_modes → full
getApiPageModeForActor / getActorPageMode: pm[pageKey] || 'full'. При рассинхроне матрицы (нет строки) пользователь получает полный доступ к разделу вместо hidden. Fix: default hidden (fail-closed); admin по-прежнему full.
2026-10-27 (прод c60e06a): default hidden в getActorPageMode / getApiPageModeForActor.
high исправлено F-ACL-03 · Грубый ACL API маркетплейсов vs матрица по магазинам
HTML: ozon/wb/yandex/issues/… — отдельные ключи; API почти всё под /exports/marketplaces → pageKey exports-marketplaces. Пользователь с parent=full и child=hidden всё равно дергает общий API всех магазинов. Обратно: только child full + parent hidden → HTML открыт, API parent hidden → 403 (ломает UX). Fix: scope в API (shop/channel) + проверка соответствующего pageKey; или отдельные prefix rules.
2026-10-27 (local): parent API mode = max(parent, children); shop/issues asserts на snapshot/export/sync/fix-*; sync-all требует parent|settings full. Parent=full по-прежнему наследует доступ к child (явный deny child при parent full — не ломали матрицу).
medium F-ACL-04 · HTML вне реестра открыт любому с сессией
isHtmlLeafAccessHidden: if (!pk) return false — незарегистрированный leaf (напр. ref/*.html, забытый экран) не скрывается матрицей. Нужна только валидная сессия. Fix: неизвестный leaf → redirect no-access (кроме явного allowlist: login, legal).
medium F-ACL-05 · Страницы без API_PREFIX (дыра покрытия)
Нет отдельного API rule: exports-marketplaces-ozon|wildberries|yandex|issues|reglament, work-schedule-settings, product (API /product → purchase), sections. Часть ок (статика), часть — связка F-ACL-03 / путаница purchase vs product.
medium F-ACL-06 · view = любой GET, включая потенциально «тяжёлые»/side-effect GET
Middleware смотрит только метод. Если где-то GET запускает sync/export — view-пользователь пройдёт. Fix: audit GET с side effects (шаги доменов); mutating только POST + assert write.
low F-ACL-07 · can_manage_users обходит hidden settings
Осознанно для управления пользователями. Риск: доступ к UI настроек шире, чем «только юзеры» (остальные секции settings зависят от фронта). Ужесточить: отдельная страница users или server-side hide блоков.
info F-ACL-08 · work-schedule OR settings; crm-task-links null на prefix
work-schedule API берёт max(work-schedule, work-schedule-settings) — ок для бухгалтерии. /exports/new-products/crm-task-links в rules = null, но роутер сам зовёт assertActorPageAccess — компенсировано.

Приоритет фиксов (шаг 2)

  1. P0: fail-closed на unmatched API + default mode hidden
  2. P1: shop-scoped ACL для marketplaces API
  3. P1: неизвестный HTML leaf → deny
  4. P2: инвентаризация GET side-effects; сузить can_manage_users UI

Шаг 4 · SQL / инъекции / query builders готово

Дата: 2026-10-25 · Скан: db.query с интерполяцией, динамический ORDER BY/LIMIT/IN, routes/mysites.js, dbAdmin.js, work.js, list-роуты (pages/medmarket/…).

Общая картина

  • Большинство list API: значения через ?, ORDER BY через whitelist map (pages, medmarketStore, suppliers, myproducts) — ок.
  • IN (...) почти везде через ids.map(() => '?') + params — ок.
  • Динамический SET col = ? в finance/productUpdates — имена колонок из кода, не из сырого body key — ок по SQLi (mass-assignment отдельно).
  • Главный риск: идентификаторы (имена таблиц/полей CMS) из конфига сайта без валидации.

Findings

critical исправлено F-SQL-01 · Second-order SQLi: поля CMS в my-sites → синк
POST/PUT /api/my-sites сохраняет table_products, field_*, wa_field_*, wa_table_skus из body без проверки идентификатора. Синк подставляет их в SQL: `… sk.${site.wa_field_sku_val} … FROM ${site.table_products}` (routes/mysites.js). Злоумышленник с правом my-sites (или admin) может выполнить произвольный SQL на БД донора CMS (и повлиять на sync в Datagon). Также SELECT id FROM ${table_products} при сохранении. Fix: whitelist /^[A-Za-z_][A-Za-z0-9_]*$/ (или schema.table с двумя частями); запрет пробелов/кавычек/точек с запятой; quoteIdent; тест на отказ инъекций.
2026-10-25 · 270624f: assertMySiteSqlIdents / quoteSqlIdent на write+sync (mysites, sync-worker, server, cms price write).
high исправлено F-SQL-02 · Пароли CMS БД в my_sites + коннект с произвольного host
Связано с F-SQL-01: db_host/user/pass хранятся и сервер коннектится наружу (SSRF-подобный к MySQL). Комбинация: подставить host + инъекция в field → exfil. Детали SSRF — шаг 14; здесь — SQL surface. Fix: allowlist хостов/VPN; encrypt db_pass; валидация идентификаторов (F-SQL-01).
2026-10-25 · 270624f: idents закрыты; GET маскирует db_pass; PUT пустой = keep.

medium F-SQL-03 · db-admin preview: динамическое имя таблицы
Есть IDENT_RE + проверка в information_schema + quoteIdent — приемлемо. Но доступ у admin или can_manage_users (шире, чем «только admin»). LIMIT численный — ок. Fix: только admin; audit log превью.

exportsNewProducts / dimensions / msSales: ALTER TABLE \` + table + \` ADD COLUMN \` + column. Обычно константы из кода — низкий риск, пока table/column не приходят из query. Fix: assert allowlist констант перед ALTER; не принимать имена с клиента.

Whitelist sort maps; IN placeholders; finance PATCH собирает фиксированные col = ?. WORK: ent.table из реестра сущностей — не из сырого path без lookup. Поставщик-label: имена таблиц — литералы в массиве кода.

Шаг 5 · XSS / CSP / HTML-вывод готово

Дата: 2026-10-25 · Скан: innerHTML / asHtml action-log, escapeHtml/esc, CSP/security headers в Node и deploy/nginx-*.conf, href из данных API.

Общая картина

  • Панель — SPA-like vanilla: сотни innerHTML = … в static-html/vanilla.
  • Паттерн «хороший»: локальный esc() / escapeHtml() + textContent; DatagonNotify экранирует title/message.
  • Паттерн «опасный»: расширенный action-log (asHtml: true) собирает HTML из фильтров / ошибок API / j.note без escape — эталон правила action-log extended буквально просит innerHTML с цифрами.
  • CSP нет ни в Node (server.js без security headers), ни в nginx (только HSTS на frontend conf). Любой XSS = выполнение скрипта без ограничений.
  • Усилитель из шага 1: токен сессии в localStorage + cookie — XSS крадёт сессию до 14 дней (обход httpOnly на cookie через дубль в LS / x-auth-token).

Сильные стороны

  • Finance cash/plan: purpose, контрагенты, ошибки банков — через esc() в таблицах и списках.
  • Processes auto-sync sections: escapeText на title/extras перед innerHTML.
  • New-products confirm collision: escapeHtml на article/code/title.
  • Product linkify: textContent для текста ссылки; URL_RE не матчит javascript: (только http(s), //, *.html, email).

Findings

high исправлено F-XSS-01 · Action-log HTML: фильтры и ошибки без escape
medmarket.scripts.html: describeAppliedFilters() вставляет f.search / code / name / medmarket_code сырьём в строку → showActionLog(…, true) → innerHTML. Фильтры пишутся в URLSearchParams (p.set("search", …)) — отражённый XSS по ссылке + клик «Заполнить коды…» (preflight тоже asHtml). В том же summary: er.code / er.error из ответа МС без esc. Аналог: my-products — describeMpAppliedFilters() (search, siteLabel), j.note, st.message, er.error в formatBulkSyncPriceSummary / hold → showMpActionLog(…, true). Issues/ops-sheet/finance имеют тот же API asHtml (finance в итогах обычно esc’ает). Impact: кража localStorage токена / CSRF-подобные действия от имени жертвы.
2026-10-27 (прод c60e06a): DatagonFmt.escapeHtml; medmarket + my-products describe/summary/errors экранируют user/API строки перед innerHTML. CSP (F-XSS-02) — отдельно.

Шаг 6 · Deploy / nginx / headers / TLS / CORS готово

Дата: 2026-10-25 · Код: deploy/nginx-p.datagon.ru*.conf, docs-docusaurus/docs/deploy.md, server.js (listen, bodyParser, HTML gate), routes/auth.js cookie, routes/workSchedule.js#clientIp.

Архитектура на краю

  • TLS на nginx → proxy_pass http://127.0.0.1:3000 (Express / pm2 parser-app).
  • Два примера: упрощённый nginx-p.datagon.ru.conf и «боевой» frontend (…-frontend.conf: QUIC, gzip, HSTS, HTTP→HTTPS 301, FastPanel includes).
  • Статика расширений (js/css/…) с root …/public + expires 30d; остальное (HTML/API) — в Node.
  • Проброс: Host, X-Real-IP, X-Forwarded-For, X-Forwarded-Proto.
  • CORS middleware в Node нет — браузерный API с чужого origin по умолчанию закрыт; фронт ходит credentials: "same-origin".

Сильные стороны

  • Frontend-конфиг: редирект :80→HTTPS; ssl_protocols TLSv1.2 TLSv1.3; HSTS 1 год.
  • Proxy на loopback Node; комментарии в conf против PHP-FPM на /.
  • disable_symlinks if_not_owner в frontend conf.
  • Отчёт аудита лежит вне public/ — nginx static root его не отдаёт.

Findings

high F-DEP-01 · Упрощённый nginx: HTTP без редиректа и без HSTS
deploy/nginx-p.datagon.ru.conf: server :80 полностью проксирует приложение (не return 301 https://…). HSTS / security headers отсутствуют на обоих server{} этого файла. При выкладке «упрощённого» примера сессия идёт cleartext; усиливает F-AUTH-03 (cookie без Secure). Fix: единый канон = frontend-паттерн (301 + HSTS); упрощённый conf либо удалить, либо сделать таким же; в deploy.md явно «не использовать conf без HTTPS-redirect».
high исправлено F-DEP-02 · Node слушает 0.0.0.0:3000 (обход nginx)
app.listen(PORT) без host → все интерфейсы. Если firewall/security-group не режет 3000 снаружи, API доступен в обход HSTS, TLS и любых будущих nginx limit_req / headers. Документация проверяет localhost:3000, но не требует bind только на 127.0.0.1. Fix: app.listen(PORT, '127.0.0.1') (или env BIND_HOST); ufw/sg: 3000 только localhost; проверка ss -lntp | grep 3000 в чеклисте деплоя.
2026-10-27 (local): default DATAGON_BIND_HOST=127.0.0.1; override 0.0.0.0 для отладки.
high исправлено F-DEP-03 · На краю почти нет security headers (кроме HSTS)
Frontend conf: только Strict-Transport-Security (+ Alt-Svc). Нет Content-Security-Policy, X-Content-Type-Options: nosniff, X-Frame-Options / frame-ancestors, Referrer-Policy, Permissions-Policy. Node тоже не выставляет (см. F-XSS-02). Clickjacking панели + нет CSP-сетки на XSS. Fix: add_header в nginx (и/или middleware в Express) с учётом нюанса nginx: add_header в location наследует не всегда — дублировать в нужных блоках; CSP сначала Report-Only.
2026-10-27 (local): Express middleware + пример deploy/nginx-p.datagon.ru-frontend.conf. На проде nginx — reload после копирования conf.
medium F-DEP-04 · Нет limit_req / rate-limit на login у nginx
В обоих conf нет limit_req_zone на /api/auth/login (и смежные). В приложении тоже нет (F-AUTH-02). Край — естественное место для первого слоя. Fix: zone по $binary_remote_addr, например 5 r/m на login + burst; 429 с понятным телом; не забыть real IP за proxy (уже есть X-Real-IP).
medium F-DEP-05 · PHP FastCGI location на корне сайта
Frontend conf: location ~ \.php$ → unix socket FastPanel, root $root_path (корень репозитория, не только public/). Любой загруженный/оставленный .php в дереве сайта исполняется вне Node ACL. Fix: убрать PHP location, если PHP не нужен; иначе root только в песочницу без секретов; запрет .php под public/ в gitignore/deploy.
medium F-DEP-06 · bodyParser.json({ limit: '32mb' }) без общего rate-limit
Глобальный JSON body до 32 МБ на любой /api — удобно для импортов, но без квот аутентифицированный (и до auth на login) клиент может долбить память/CPU. Fix: меньший default (1–2mb) + точечно больший limit на upload-роутах; nginx client_max_body_size; connection limits.
medium F-DEP-07 · Доверие к X-Forwarded-For без trust proxy
workSchedule.clientIp берёт первый IP из XFF. Express trust proxy не включён. Клиент, бьющий Node напрямую (F-DEP-02) или при неверной схеме proxy, подставляет любой IP в audit/clock. Fix: app.set('trust proxy', 1) только за nginx; IP = req.ip; не принимать XFF от не-прокси.
low F-DEP-08 · HSTS без includeSubDomains; IP сервера в git
HSTS: max-age=31536000 без includeSubDomains / preload. В conf зашит listen 155.212.171.103:… — инфраструктурный IP в репозитории. Fix: при политике поддоменов — includeSubDomains; listen на */0.0.0.0 или плейсхолдер в примерах; IP не коммитить.
info F-DEP-09 · CORS не настроен (same-origin OK); публичные /docs и ArchitectUI
Отсутствие CORS — нормально для same-site панели. HTML gate в server.js пропускает без сессии /docs* и /architectui-react-pro* — осознанно для справки/демо; детали утечек — шаг 19. Убедиться, что в docs нет секретов/внутренних URL с токенами.
info F-DEP-10 · TLS 1.2/1.3 и proxy headers — ок
Протоколы современные; ssl_prefer_server_ciphers off (упрощённый) — приемлемо для TLS1.3. Проверить на проде актуальный сертификат (в frontend conf имя файла с датой 2026-04-30) и автообновление.

Приоритет фиксов (шаг 6)

  1. P0: bind Node на 127.0.0.1 + firewall; HTTPS-only nginx (301 + HSTS на всех conf)
  2. P0: Secure на dg_session (F-AUTH-03) согласованно с HTTPS
  3. P1: security headers + CSP Report-Only; limit_req на login
  4. P2: убрать/изолировать PHP location; уменьшить JSON body limit; trust proxy = 1

Шаг 7 · Settings + users + specialties готово

Дата: 2026-10-25 · Код: routes/settings.js, routes/auth.js (users/password), routes/specialties.js, lib/datagonSpecialties.js, middleware ACL в server.js, UI settings.scripts.html.

Модель доступа

  • admin (username): обход матрицы; CRUD пользователей; матрица специальностей; всё settings.
  • can_manage_users: открывает /settings.html даже при settings=hidden (shell только «Пользователи»); API bypass только /api/auth/users* (все методы) + GET /api/specialties*. Создаёт пользователей; не может выдать «Полный доступ», менять чужие записи, archive/delete, permissions.
  • Матрица settings: view → GET settings (секреты plaintext — F-SEC-02); full → POST ключей, auto-sync, retention и т.д.
  • Запись специальностей / матрицы режимов — только admin (роутер specialties).

Сильные стороны

  • Нельзя назначить «Полный доступ» при создании не-admin’ом; новый user всегда can_manage_users=0.
  • Нельзя удалить/архивировать встроенного admin; нельзя удалить системную специальность с пользователями.
  • UI shell менеджера скрывает глобальные настройки; смена пароля чужого — только admin.
  • Whitelist полей POST /api/settings (не mass-assignment произвольных ключей).
  • Архив пользователя → revoke сессий.

Findings

high F-SET-01 · Один page-key settings = секреты + расписание + опасные действия
Любой с settings=view|full читает ozon/wb/ym/huckster/proxy keys (F-SEC-02). С full — перезаписывает ключи, retention, формулы продаж, прокси. Менеджер пользователей без settings в матрице секреты не получает (хорошо), но любая «широкая» специальность с settings=full = полный контроль интеграций. Fix: разделить page keys (settings-users / settings-integrations / settings-autosync); GET secrets только admin или write-only masks.
high исправлено F-SET-02 · POST /api/settings/auto-sync-run — любой settings=full
Эндпоинт в server.js ставит в очередь любую задачу из реестра (цены CMS, МС, финансы Точка, marketplaces, …) без доп. роли. Abuse: нагрузка на МС/МП, перезапись цен, гонки с продом. Нет server-side confirm / idempotency token / audit aparte от auto_sync_runs. Fix: только admin или отдельный mode; rate-limit; для destructive задач — обязательный confirm: true + запись в activity с user_id.
2026-10-27 (local): admin всегда; иначе settings=full + confirm: true (UI «Запустить сейчас»). 403 AUTO_SYNC_RUN_FORBIDDEN.
medium F-SET-03 · Middleware bypass /auth/users* на все методы
can_manage_users → next() для любого метода на /auth/users…. Сейчас handlers режут archive/delete/put/permissions до admin — ок, но новый маршрут без проверки = мгновенная эскалация. Create user позволяет плодить учётки (phishing / шум). Fix: bypass только GET list + POST create; остальное — через матрицу/admin; audit уже есть на create — расширить алерты.
medium F-SET-04 · Смена пароля без текущего (self) + admin reset
POST /api/auth/change-password: достаточно сессии; поле текущего пароля нет (см. F-AUTH-04). Украденный token (XSS/LS) → смена пароля + revoke чужих сессий жертвы = полный захват. Admin reset чужих — ожидаемо, но без step-up. Fix: для self требовать currentPassword; для admin — re-auth / TOTP.
medium F-SET-05 · Специальностей: имя без UNIQUE; rename системной
Защита «Полный доступ» завязана на name === 'Полный доступ'. renameSpecialty может переименовать системную; можно создать дубликат имени (нет UNIQUE). Тогда запрет менеджеру на «Полный доступ» обходится второй одноимённой специальностью с нужными mode, либо ломается seed/default lookup. Fix: is_system флаг; UNIQUE(name); запрет rename/delete system id; запрет assign по флагу, не по строке.
medium F-SET-06 · DELETE user без revoke сессий / без FK CASCADE
DELETE FROM users без предварительного revoke (в отличие от archive). Таблица auth_sessions без явного ON DELETE CASCADE в ensureAuthSchema — риск сиротских сессий или ошибки FK / висящих hash. Fix: revoke + delete sessions в той же транзакции; FK ON DELETE CASCADE.
low F-SET-07 · Пустая строка в POST settings затирает API key
if (ozon_api_key !== undefined) … String(ozon_api_key || '') — явная отправка "" очищает ключ. UI verify ловит часть случаев, но гонка/баг формы = outage интеграций. Fix: write-only: пустое = «не менять»; отдельный clear с confirm.
low F-SET-08 · isAdmin/canManageUsers в localStorage
UI читает флаги из LS (можно подделать и увидеть чужие формы). API всё равно режет — не RCE, но путаница + лишний attack surface для XSS (показ секретных полей до 403). Fix: только из /api/auth/me в памяти; не персистить роли в LS.
info F-SET-09 · Хорошие инварианты (зафиксировать регрессионными тестами)
Менеджер ≠ Full Access; permissions только admin; specialties write только admin; users-manager shell; whitelist POST settings; activity log на create/archive. Имеет смысл jest/supertest на эти 403/400.

Приоритет фиксов (шаг 7)

  1. P0: маски секретов в GET + разделение page keys / auto-sync только admin (F-SET-01/02, F-SEC-02)
  2. P1: currentPassword на self change-password; revoke при DELETE user
  3. P1: is_system + UNIQUE на specialties
  4. P2: сузить middleware bypass; write-only keys; роли не в localStorage
